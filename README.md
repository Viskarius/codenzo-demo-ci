# Codenzo demo CI/CD

Простой демо-проект:

- линтер: ESLint;
- тесты: node:test;
- CI/CD: GitHub Actions;
- деплой: VPS + Nginx через rsync/SSH;
- мониторинг: внешний uptime-check для /healthz.

Локальные проверки:

1. npm install
2. npm run lint
3. npm test

## CI/CD пайплайн

Пайплайн реализован через GitHub Actions (`.github/workflows/ci-cd.yml`) и состоит из двух джобов.

1. **checks (линтер и тесты).** При пуше в `main` GitHub поднимает ubuntu-latest, чекаутит код, ставит Node.js 20 и зависимости через `npm ci` (гарантирует идентичные версии пакетов на CI и локально), затем запускает ESLint и тесты на встроенном раннере `node:test`.
2. **deploy.** Запускается только после успешных проверок. Раннер подключается к VPS по SSH с ключом из GitHub Secrets и синхронизирует `public/` с `/var/www/codenzo-demo` через `rsync --delete` (удалённые из репозитория файлы исчезают и на сервере). Nginx отдаёт статику пользователям.

Почему так: проект на раннем этапе, Kubernetes и сложные оркестраторы не нужны. GitHub Actions бесплатен и живёт прямо в репозитории; связка VPS + Nginx + rsync прозрачна, не привязывает к проприетарному хостингу и легко поддерживается.

## Мониторинг доступности

Базовая схема: внешний uptime-мониторинг (UptimeRobot, бесплатный тариф) проверяет `http://<host>/healthz` каждые 5 минут и ожидает HTTP 200 с телом `ok`. Эндпоинт лёгкий: Nginx отвечает на него без обращения к диску, поэтому проверка не создаёт нагрузки. При двух-трёх неудачных проверках подряд сервис шлёт алерт на почту/в Telegram.

Мониторинг именно внешний: если проверочный скрипт держать на том же VPS, он упадёт вместе с сервером и не сможет сообщить о проблеме. Позже, с появлением бэкенда, добавим Sentry для ошибок клиентского JS и алерты на рост 5xx.
